# PlayGround — магазин ключей, Prime, Dota Plus и скинов CS2 / Dota 2

Next.js 15 (App Router) + TypeScript + Tailwind 4 + PostgreSQL + Drizzle ORM.
Оплата только ELQR в сомах, товар выдается только по webhook провайдера с проверенной подписью.

## Запуск локально

```bash
cp .env.example .env              # заполнить DATA_ENCRYPTION_KEY, MOCK_ELQR_WEBHOOK_SECRET, CRON_SECRET, SESSION_SECRET (+ STEAM_API_KEY)
docker compose up -d              # PostgreSQL 16
npm install
npm run db:migrate
npm run db:seed                   # тестовые товары и ключи (только для разработки!)
npm run dev                       # http://localhost:3000
npm run admin:grant -- you@example.com   # после первого входа: сделать себя администратором (/admin)
```

Секреты: `openssl rand -base64 32` для DATA_ENCRYPTION_KEY, `openssl rand -hex 24` для остальных.

Тесты (нужна база `shop_test`, `createdb -O shop shop_test` и `DATABASE_URL=...shop_test npm run db:migrate`):

```bash
npm test
```

## Как проверить покупку

1. Главная → CS2 Prime Status → «Купить» → email + 18+ + оферта.
2. На странице заказа QR и таймер 15 минут. В режиме `PAYMENT_PROVIDER=mock` есть ссылка «страница тестового банка».
3. «Оплатить» в тестовом банке → банк шлет подписанный webhook → страница заказа сама показывает ключ.
4. Письмо с ключом — на `/dev/mail` (без SMTP письма никуда не уходят). Для реальной отправки: `EMAIL_TRANSPORT=smtp` и `SMTP_*` в `.env`.

## Правила, которые нельзя ломать

- Нет кейсов, рулеток, случайных выдач, пополняемого баланса покупателя и вывода. Баланс есть только у продавцов P2P: заработок со сделок минус выплаты на их реквизиты; корректировка админом — с причиной и в журнале. Кейсы и капсулы фильтруются при синхронизации инвентаря и выставлении лотов.
- Выдача только в `handlePaymentWebhook` после проверки подписи. Опрос статуса через API провайдера товар не выдает, а только ставит заказ на проверку.
- Один заказ = один платеж; повтор webhook ничего не выдает второй раз.
- Оплата по просроченному заказу уходит на автоматический возврат.
- Деньги в тыйынах (integer), валюта только KGS.

## Подключение реального провайдера

Создать `src/lib/payments/<provider>.ts`, реализующий `PaymentProvider` (createQr, getStatus, verifyWebhook, refund), добавить в `getPaymentProvider` и в enum `PAYMENT_PROVIDER` в `src/lib/env.ts`. Логику заказов менять не нужно.

## Воркер Steam-ботов

Отдельный долгоживущий процесс (Railway / VPS). Запускать **один** экземпляр.

```bash
BOT_MODE=mock npm run worker      # без Steam: mock-бот с примерами предметов, трейды «принимаются» через 30 с
```

Боевой режим: `BOT_MODE=steam` и `STEAM_BOTS` (JSON: name, username, password, sharedSecret, identitySecret) —
секреты ботов только в env воркера. Остальные переменные — как у сайта (общая база).
float и паттерн CS2 — через `FLOAT_INSPECT_API` (формат CSFloat Inspect), без него поля пустые.

Что делает: раз в 10 минут синхронизирует инвентарь в скрытые карточки без цены (цены — в `/admin/bots`),
отбрасывает кейсы, ключи, капсулы и прочие контейнеры; каждые 15 секунд отправляет трейды из очереди
(повторы до 5 попыток), проверяет принятие, не принятые за `tradeAcceptHours` отменяет и переводит заказ в «Проблема».
В mock-режиме: trade-ссылка с `token=decline…` — отказ, `token=hold…` — trade hold, `token=fail…` — ошибка Steam.

## P2P-маркет (этап 6, выплаты только mock)

Пользователи выставляют скины из своего инвентаря Steam (`/sell`), покупатели платят по ELQR, продавец передает скин
трейд-оффером, сайт проверяет получение по инвентарю покупателя. После защиты от отката (`p2pProtectionDays`) заработок
начисляется на баланс продавца и автоматически уходит выплатой — только верифицированному продавцу, только на реквизиты
на его имя, в пределах лимитов. Не передал за `p2pTransferHours` — сделка отменяется, покупателю полный возврат.

- Связанные аккаунты (общий IP, устройство — cookie `pg_did`, одинаковые реквизиты) и цена дальше ±`p2pMaxPriceDeviationPercent` %
  от рынка → сделка «На проверке», решает комплаенс (`/admin/deals`).
- Верификация: `/sell/verify` → очередь `/admin/verification` (только роль COMPLIANCE). ФИО, паспорт, телефон и реквизиты
  шифруются в базе, фото паспорта и селфи шифруются и лежат в приватном хранилище (`FILE_STORAGE=s3` на боевом).
- Проверка сделок: воркер (раз в минуту) или крон `GET /api/cron/p2p` с `Authorization: Bearer $CRON_SECRET`.
- Выгрузка истории сделок и выплат: кнопки на `/admin/deals` (CSV).
- Режим разработки (`STEAM_CHECKS=mock`): инвентари Steam тестовые, на странице сделки у продавца есть кнопка
  «Передать предмет (тест)».

Реальные выплаты подключаются в этапе 8, после того как провайдер согласует маркетплейс-схему.
